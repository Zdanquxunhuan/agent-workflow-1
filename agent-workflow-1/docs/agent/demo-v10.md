# V10 面试演示与部署演练手册

2026-11-05：这是待执行手册，尚无本轮演示、测试或部署通过记录。使用合成订单、sandbox 网关、独立的申请人与主管账号。开发者本轮未编写自动化测试，也未执行以下步骤。

## 一条主线，约 8–10 分钟

1. **需求不完整**：在 `/dialogue.html` 使用申请人身份输入“帮我看看能不能退款”。展示 WAITING_INPUT、固定问题模板、没有占用模型连接；记录 `runId`。如果模型非法猜测订单号，服务器同样转为缺参澄清。
2. **补充信息**：输入合成编号 ORD-1001。显示恢复仍是同一 run、累计次数不归零，旧身份没有入库；订单和政策重新查询，最终答案显示本阶段来源。假定测试政策是“已发货订单退款需要主管审批。”，不要把模型答复当作批准。
3. **解释计划**：展开计划回放，说明原始计划、缺参暂停、USER_INPUT 新版本和 QUERY/ANSWER 动作。另用一个本地知识无结果 fixture 演示一次 NO_EVIDENCE→改写→成功；不在真实供应商上随机碰运气，不反复试到满意。
4. **展示记忆边界**：切到 `/memory.html`，通过既有 V7 页面显式保存并确认“回答简洁”的偏好，再到 `/conversation.html` 新建 V6 会话并追问。说明 V10 澄清链只持有本次原问题和补充数据，V6/V7 是独立的会话/记忆入口；没有声称 V10 页面自动读取偏好。
5. **用户明确申请退款**：申请人使用原 `POST /api/v1/tasks`，独立 `Idempotency-Key`，请求体 `{"request":"为订单 ORD-1001 退款 20 元"}`。这是一次新的业务指令，由原计划校验与审批规则生成独立 writeTaskId；query runId 仅作为演示记录关联，不构成授权凭据。
6. **独立审批**：申请人尝试自批应被拒绝；另一个主管主体调用 `POST /api/v1/tasks/{writeTaskId}/approve`，可用 `{"reason":"合成演示订单已核对"}`。等待原 Outbox/外部命令状态变化，用任务视图和 `GET /api/v1/commerce/orders/ORD-1001` 核对结果；“已受理”与“已完成”分开解释。
7. **确认幂等与停止**：同一个写幂等键重复提交/重复审批不得重复退款。演示另一条等待中的只读 run 被取消后不可恢复；不要取消已被外部受理的退款，也不要通过 V10 重规划重放写操作。

若需改变退款金额、订单或其他关键参数，应重新明确申请并走新审批；当前没有“聊天修改既有已批准任务”的能力。演示中不能将自然语言查询结果、记忆偏好或澄清输入当成写授权。

## 直接查看的接口

创建：`POST /api/v1/agent/dialogues`，带 JWT 与唯一 `Idempotency-Key`，正文 `{"message":"帮我看看能不能退款"}`。

补充：`POST /api/v1/agent/dialogues/{runId}/inputs`，带新幂等键，正文 `{"revision":0,"field":"orderId","value":"ORD-1001"}`。以当前状态返回的 revision/field 为准，不硬编码所有轮次为 0。

观察：`GET /api/v1/agent/runs/{runId}`、`/usage`、`/events` 和 `GET /api/v1/agent/dialogues/{runId}/plans`。最终答案仅从 `GET /api/v1/agent/runs/{runId}/result` 获取。取消：`POST /api/v1/agent/runs/{runId}/cancel`。

## 一次有限部署/故障演练

准备隔离 MySQL、RAG/MCP 本地 fixture、两个主体、明确价格及预算；按 [V10 说明](version-10.md) 升级 V12 并启用配置。由后续执行者一次完成正常主线后，只增加以下三个故障点，不做长时间跑量：

| 故障点 | 应见行为 |
| --- | --- |
| WAITING_INPUT 后重启 Java | 等待记录保留、没有自动模型调用；新 JWT 可恢复，旧 JWT 未保存 |
| 等待期间撤销知识/物流来源权限 | 恢复前校验拒绝，任务停止；不能换工具绕过或读取旧答案 |
| 模型调用已预留时进程丢失 | deadline 后保守结算 unknown，重启不自动重放，晚响应不重复结算 |

回退先停止新流量，取消/排空旧 run，等待审计收尾；不可让旧二进制读取新 WAITING_INPUT 状态。清理用隔离环境的既有保留制度，不写生产库删除脚本。

## 面试讲解提纲

**场景**：售后查询往往缺少订单号，遇到没有证据或权限变化时，Agent 需要询问、有限调整或停止，而不是一直尝试。

**核心设计**：Spring AI 负责模型协议；执行器控制工具权限和状态；同一 run 保留预算；MySQL 原子暂停/恢复；RAG/MCP 提供当前证据；写链路独立审批与幂等。主动选择滚动只读计划，而不是引入多 Agent 或一个自由执行脚本。

**两个竞争问题**：补信息与取消同时到达时由行锁决胜；旧 worker 暂停后立即有新输入时，旧 worker 必须直接退出，不能结束新阶段。发布答案和取消也共用 run 锁。

**成本真实性**：记录调用次数、provider usage、unknown 预留、价格版本和总执行时长；不把预估 token 当供应商实测，不把进度 SSE 说成正文 token 流，不声称没有验证过的节省比例。

**诚实边界**：V5 有既有有限验证；V6–V10 当前代码不等于生产业绩。用后续真实验证报告说明已通过内容；没有报告时明确未验证。当前优先补证据、练讲解，后续版本应由真实失败或面试反馈驱动。

## 演示记录模板

记录日期/提交 SHA、环境与身份、query runId/taskId、writeTaskId、计划版本及终止原因、每次调用/用量、累计估算费用、请求至待补/最终答案的耗时、写入前后退款记录数量。每个条目只填实际观测；当前均为待采集。日志/截图不要带访问令牌、密钥、个人信息或未经授权的资料正文。
