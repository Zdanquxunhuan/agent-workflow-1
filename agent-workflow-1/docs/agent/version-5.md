# Version 5：Spring AI 与 Java Agent 的安全 RAG 闭环

日期：2026-11-03。状态：**本地实现与小样本验证完成，未部署，未完成生产验收。** 当前范围见 [交付说明](delivery-v5.md)、[验证记录](verification-v5-2026-11-03.md)、[框架 ADR](adr-001-spring-ai.md)。总路线见 [版本计划](../../rag-production-to.md)，需求依据见 [岗位差距](../../toAjob-distance.md)。

以下保留最初执行计划作为目标基线，未勾选清单不代表全部尚未实现；当前交付和未完成项以上述交付说明与验证记录为准。企业委托、生产部署及完整验收仍未完成，不把有限本地验证改写成全部目标达成。

## 1. 本版要解决的问题

V4 已能在 Python 知识问答入口返回带引用的单轮答案，但 Java 仍使用手写模型 HTTP 网关，任务、聊天审计、幂等和恢复尚未建立完整 tenant 边界，远程知识工具因此保留 `RAG_TASK_TENANCY_REQUIRED`。直接加记忆会把这条未隔离链路持久化；继续增加 RAG 管理功能又不能补 Java AI 框架实战。

**V5 的目标是：用户从 Java 入口查询一个订单的售后条件，Agent 通过 Spring AI 调用受控只读工具，取得当前业务事实和有权访问的政策证据，返回可追溯答案；身份、存储、回放和恢复保持同一授权边界。** 本版主要覆盖 J01/J04/J05/J06，并为 V6/V7 记忆铺路。

保留现有 [Java 显式状态机](../adr-002-workflow-framework.md) 与 [独立 RAG 服务边界](../rag/adr-001-service-boundary.md)。写操作继续走原任务、审批、幂等、Outbox 与外部确认流程；知识证据不直接批准退款。

## 2. V5A：框架适配，先保留应用侧执行控制

- [ ] 以当前 `pom.xml` 的 Java 17 / Spring Boot 3.5.16 为兼容基线，核对 Spring AI 正式版本的 Java/Boot/Provider 支持，锁定 BOM 与实际依赖；不直接套用最新文档或自动升级主项目。若兼容性要求改变，先记录成本和方案。
- [ ] 增加 `ToolCallingGateway` 的 Spring AI 适配，用 `ChatModel` 等模型抽象转换现有 messages、工具定义、tool calls 和最终回复。保留旧适配器作为显式配置的对照/回滚选项，不在故障时隐式切换并重复执行。
- [ ] 工具执行只走现有 `ToolRegistry` 与应用侧最多 4 轮循环；关闭或接管所选版本的框架自动执行路径，避免外层循环和框架循环叠加。只读白名单、参数校验、角色和审计仍由服务端决定；身份信息由可信上下文注入，不能作为模型可填写的授权参数。
- [ ] 为 Provider、Prompt 与工具 schema 建立可追踪版本；扩展响应元数据保存 model、provider usage/unknown、调用耗时、错误和 trace。模型原始输出、密钥和完整业务正文不作为默认日志。
- [ ] 用同一小组业务只读样例比较现有网关和框架适配：工具选择、参数、失败行为与接入成本；形成一份简短 ADR。`TaskPlanner` 后续可复用统一模型适配，本版不要求同时重写所有规划器。

选型建议基于当前 Spring 工程和已有接口，而非框架排名。已核对的 [Spring AI 1.1 工具调用文档](https://docs.spring.io/spring-ai/reference/1.1/api/tools.html#_user_controlled_tool_execution) 提供调用方控制工具执行的方式，适合渐进适配；这不等于已经验证具体依赖兼容性。实施时使用锁定发布版对应文档，不混用不同大版本 API。只引入一个 Java AI 框架，LangChain4j 留在选型对照中。

V5A 可先独立验收；此时远程 RAG 任务门禁仍保留，不能把“加了框架依赖”记成 V5 完成。

## 3. V5B：主体、租户和持久授权委托

| 改造面 | 最小完成要求 |
| --- | --- |
| 入口与主体 | 从已验签令牌获得 tenant/subject/角色与允许范围，贯通 `AuthenticatedUser`、`ToolContext`、规划与工具执行；缺失或冲突时失败关闭，不信任自报 Header、请求体或模型参数 |
| 任务与权限 | task、step/result、event、chat audit、audit outbox、审批/恢复记录具有一致 tenant；查详情、列表、事件、取消、审批、恢复都检查 tenant 与 owner/操作权限；tenant 相同不等于可读别人的任务 |
| 幂等与回放 | 唯一键至少包含 tenant、发起主体、操作和幂等键，并验证请求摘要；重放前重新授权，缓存成功响应不能绕过失权/证据失效检查；不同租户相同 key 不互相回放 |
| 业务工具 | tenant/主体约束传到订单、支付等数据授权和下游服务；不能只隔离任务表而共用无边界业务记录。旧适配器若仍为单租户，显式限定唯一租户，对其他租户禁用；不能宣称业务系统全链路多租户 |
| 历史迁移 | 新增 Flyway 迁移并记录旧数据归属规则、复合索引/约束、读写切换与回退限制；不能从 userId 猜 tenant，也不能让 NULL tenant 匹配任意主体。内存模式与 JDBC 模式保持相同隔离语义 |
| 后台委托 | 持久记录 tenant、原主体、任务、授权范围、目标 audience、有效期、撤销状态和授权引用；服务端凭该引用向受信服务取得短期凭据，重新校验当前成员/资源权限；委托只能收窄权限 |
| 恢复与失效 | 后台不能依赖原请求线程的 `SecurityContext`，不持久保存用户 Bearer token；过期、撤权或无法重获授权时停止并记录可操作原因，不能以超级服务账号代用户继续读取 |

完整 V5 需要可运行的委托取得/校验路径及恢复用例，不只定义一个接口。可以先用本地受信身份服务与合成主体做隔离演示，但须明确企业 IdP 联调尚未完成；无委托实现的路径继续关闭。审批人的操作权限与原申请人的资料访问权限分开检查。

涉及已经受理的外部写操作时，原有对账仍按受控服务权限进行，避免丢失结算状态；用户失权不意味着重新提交写操作，也不意味着允许向该用户返回受限详情。

## 4. V5C：真实 RAG 与业务工具联合回答

请求职责保持清晰：

| 入口 | 主要回答生成方 | 行为 |
| --- | --- | --- |
| 独立知识问答 `/api/v1/answers` | Python V4 Provider | 继续使用既有单轮证据/引用规则 |
| Java `/api/v1/agent/chat` | Java Spring AI 适配 | 调用业务只读工具和 RAG `/search`，由 Java 生成并校验最终回答；不再调用 Python `/answers` 生成一次后让 Java 改写 |
| Java `/api/v1/tasks` 与恢复 | 既有 Java 状态机 | 工具结果携带授权证据与来源；读取/回放/恢复时校验，写操作沿用审批和外部结果确认 |

- [ ] 明确本次允许的 KB 范围和租户模型出域策略；模型选择工具不等于能扩大知识库/业务数据范围。
- [ ] 将知识证据与业务事实分开标注：政策结论引用 document/version/chunk/hash/content revision 与原文摘录；订单事实指向当前工具结果和查询时间，不伪造为政策引用。
- [ ] 为所有送入模型的知识来源保存定位与版本快照，最终返回前复核当前权限、删除状态和版本修订；引用必须属于本次来源且摘录匹配。通过引用结构校验不代表语义必然正确。
- [ ] RAG 现有引用接口若不足以核对全部快照字段，补最小的授权证据复核契约与契约测试；Java 不直连 PG，不以“刚才检索过”替代复核。来源不可读或已变更时不返回生成正文。
- [ ] 任务结果/聊天审计中的派生正文必须关联来源；后续查询与幂等回放也做权限/失效处理，不能只保护原文引用 URL。元数据和审计按最小内容保存。
- [ ] 无政策证据时明确证据不足；业务工具失败、RAG 限流/超时、模型无效输出与无证据分别表达；不回退本地演示资料，不根据知识库内容修改系统指令或执行写工具。
- [ ] 整个请求共享 deadline、工具调用数/结果体积/输入输出上限；Provider 隐式重试受同一预算控制。真实 usage 缺失标为 unknown，估算 token 与账单用量分开；完整费用路由策略归 V9。

只在 V5B 隔离和 V5C 门禁验收后替换当前“一律阻断任务 RAG”的限制。未迁移路径、缺凭据和无授权范围继续失败关闭；不能简单删掉 `RAG_TASK_TENANCY_REQUIRED` 条件。

## 5. 验收清单与演示材料

优先复用已有合成订单/政策和隔离测试环境，新增少量关键样例。下列是计划场景，不是已运行结果；真实模型只做必要的代表性联调，权限/故障时序主要用可控替身验证。

| 场景 | 通过条件 |
| --- | --- |
| 框架与工具控制 | Spring AI 真实模型提出只读工具调用并由注册表执行；未知/写工具、额外参数、超过轮数均被阻止；原审批和业务幂等不回退 |
| 正常联合回答 | Java 入口查一个合成订单及对应政策，拿到真实 RAG 证据并返回可读取引用；记录实际启用的 embedding/rerank/LLM 链路，部分替身不能称全模型联调 |
| 双租户与同租户双主体 | 相同幂等键、伪造 taskId、查看事件/聊天审计、审批/取消/恢复都不串数据；业务工具也拒绝不属于主体范围的订单 |
| 失权、换版与回放 | 模型执行中撤销 ACL/切换版本后不返回旧答案；已保存的结果、审计正文或幂等响应不能泄露；全部送模来源都参与复核 |
| 后台恢复 | 模拟进程重启/原令牌过期，有效委托可继续授权的只读步骤；委托失效则停止；不重做已受理的退款等副作用 |
| 故障与预算 | 无证据、RAG 429/超时、Provider 故障、无效引用、预算耗尽有不同结果；无隐藏循环重试、无故障回 demo |
| 数据升级 | 在隔离库验证旧数据归属、唯一约束与迁移后读写；正式工作库升级、企业 IdP 与生产验收另行记录 |

交付时附：框架选型 ADR、配置/迁移说明、接口变化、验收报告、一个可重放的演示脚本，以及“Java 入口 → 模型 → 工具 → RAG → 最终门禁”的调用链。报告写清真实运行环境、失败案例与未执行项，不沿用 V3/V4 数字充当 V5 成绩。

面试重点可以围绕三件事展开：为什么让框架负责模型适配而保留执行控制；为什么任务租户化必须涵盖回放和恢复；为什么引用正确仍不等于语义正确。这些问题有代码路径和失败场景支撑后，再写入简历。

## 6. 本版范围边界与后续

V5 不承诺跨请求对话；“那运费呢”这类需要历史的追问归 V6。长期记忆归 V7，一个只读 MCP 服务归 V8，流式/两模型路由/费用控制归 V9，受控重规划与最终部署演练归 V10。

OCR、批量上传、整库影子重建、更多向量数据库、GraphRAG、复杂多 Agent 协作继续留在按需增强/生产待办中。V5A/B/C 的当前范围已较大，允许逐项交付，但不能通过省略租户和证据门禁换取“完整 V5”标签。
