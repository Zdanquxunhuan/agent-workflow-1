# 生产就绪审查与上线门槛

## 结论

当前版本不能直接接入生产业务，也不能直接执行真实退款、地址修改或其他有副作用的操作。它已经达到“可运行、可测试、可演示的安全执行内核”水平，适合继续做内部 PoC、架构评审和接入适配器前的回归基线。

当前全量测试通过，但测试主要覆盖内存仓库、固定模拟数据和离线确定性规划器。测试通过不等于生产系统已经完成身份、数据、并发、外部依赖和运维验收。

本次补充的代码改进：DeepSeek 多轮 Tool Calling 网关现在使用 `agent.deepseek.timeout-seconds` 设置连接/读取超时，并对瞬态错误和 429 限流做最多一次有限重试。只读模型请求可以安全重试，但真实业务写操作不能套用这条策略。

## 2 阻断上线的 P0 问题

### P0.1 身份认证和权限来源不可信

当前 `TaskController` 和 `AgentChatController` 直接读取 `X-User-Id`、`X-Role`。任何能访问服务的人都可以伪造主管或管理员身份。`ToolRegistry` 的权限判断本身是正确的，但它判断的是未经认证的输入。

生产改造要求：

1. 在 API Gateway 或 Spring Security 中验证 OIDC/JWT/mTLS。
2. 从已验证的 token 读取 subject、租户、角色和权限，不接受客户端自填角色。
3. 把身份封装成 `AuthenticatedPrincipal`，应用服务只接受该对象，不再让业务代码依赖原始请求头。
4. 审批时校验租户、组织、任务归属和职责分离，禁止申请人审批自己的高风险任务。

### P0.2 真实外部工具和业务幂等还不存在

现在的 `OrderQueryTool`、`RefundTool`、`AddressUpdateTool` 都是模拟实现。真实适配器必须处理：

- 下游超时、限流、5xx、部分成功和结果未知。
- 业务幂等键下沉到支付、订单和物流系统。
- 请求签名、凭据轮换、连接池和 TLS。
- 外部状态查询和人工对账。

不能把 `simulation=true` 替换成“调用真实接口”就直接上线。写操作必须先定义“请求已受理”“执行成功”“执行失败”“状态未知”四种结果，并对状态未知进入人工处理或对账队列。

### P0.3 默认内存存储和完整事务边界

默认配置是 `AGENT_PERSISTENCE=memory`，进程重启会丢失任务和事件。JDBC 适配器虽然存在，但当前：

- `DriverManagerDataSource` 没有生产连接池配置。
- `create` 的长流程包含模型调用和工具调用，不能被一个长数据库事务包住。
- 本次已增加 `TaskAuditWriter`、V3/V4 迁移和 `AuditOutboxPublisher`，每次任务快照、对应审计事件和待发布 outbox 记录在同一资源事务中写入；发布器已有租约、失败退避和幂等标记，真实下游事件总线仍需接入。
- 没有 Outbox、事件重放、归档和保留策略。

生产改造要求：

1. 生产配置禁止 memory profile，启动时缺少 JDBC 配置直接失败。
2. 使用 HikariCP 或平台连接池，配置最大连接数、超时、泄漏检测和只读连接。
3. 保留 `TaskAuditWriter` 的单次写入事务边界，接入真实下游事件总线、监控和死信处理。
4. 使用 Outbox 表将状态变更和审计事件放入同一数据库事务，再由发布器投递到事件总线或 SIEM。
5. 对 `user_id + idempotency_key`、任务状态版本和审批版本建立唯一约束/乐观锁。

### P0.4 多实例幂等不是 JVM 级别

`AgentApplicationService.create` 使用 `synchronized`，`approve` 使用任务对象锁。这只能保护单个 JVM。多副本部署时，两个实例可能同时读取和审批同一个任务。

生产改造要求：

- 以数据库唯一约束保证创建幂等。
- 以 `version` 乐观锁或 `SELECT ... FOR UPDATE` 保护审批和状态迁移。
- 重复请求返回同一个结果，竞争更新返回明确的 `CONFLICT`。
- 编写两个应用实例同时审批的集成测试，而不是只测单进程线程竞争。

### P0.5 同步 HTTP 执行不适合长任务

当前 `POST /tasks` 会在 HTTP 请求中完成规划和工具执行，deadline 默认 30 秒。真实模型和业务系统可能超过网关超时，客户端断开也不代表服务端停止了外部写操作。

生产改造要求：

```text
POST /tasks -> 写入任务 + 投递命令 -> 202 Accepted + taskId
Worker -> 规划/审批/执行 -> 持久化状态和事件
Client -> GET /tasks/{id} 或订阅事件
```

需要队列、Worker、取消语义、死信队列和人工处理队列。审批也应是独立命令，不应依赖原始 HTTP 请求仍然存活。

## 3 P1 重要缺口

### P1.1 Checkpoint 不是独立持久化状态

当前 `Checkpoint` 是执行循环中的对象，主要通过 `CHECKPOINT_SAVED` 审计事件表达；恢复时根据已成功的 `task_steps` 推导下一步。进程可能在外部写操作已产生效果、但步骤尚未提交时崩溃，恢复无法仅凭本地状态判断外部结果。

生产方案：

- 增加独立 `task_checkpoints` 表和版本号。
- 写工具执行前生成业务幂等键并持久化。
- 写工具返回不确定时进入 `UNKNOWN_SIDE_EFFECT`，禁止自动重放。
- 通过外部查询、对账或人工审批确认后再关闭任务。

### P1.2 RetryPolicy 尚未覆盖工具执行

当前 `RetryPolicy` 主要用于 DeepSeek 规划请求；`AgentApplicationService.executePlan` 没有一个统一的工具重试执行器。生产不能用“所有异常都重试”的方式补上，因为写操作可能重复产生副作用。

建议新增 `ToolExecutor`，按工具契约声明：

| 工具类型 | 可重试条件 |
| --- | --- |
| 只读查询 | 连接失败、429、部分 5xx，可在 deadline 内有限重试 |
| 幂等写操作 | 只有下游确认幂等键后才允许有限重试 |
| 非幂等写操作 | 不自动重试，状态未知进入人工队列 |
| 参数/权限/业务拒绝 | 不重试 |

### P1.3 ContextBuilder 没有接入完整规划链

`ContextBuilder` 已经可以限制当前任务请求和最近步骤，但当前主规划器仍主要接收原始 request；聊天现在有任务审计，但还没有独立的 conversation context 存储。生产模型上下文需要：

- 只传当前任务、当前租户和必要的授权证据。
- 明确截断、token 预算和敏感字段脱敏。
- 把数据库结构化状态作为事实源，不把模型历史当作最终状态。
- 记录 prompt/model/version，便于复盘和成本分析。

### P1.4 聊天入口的生产审计仍需完善

`/api/v1/agent/chat` 现在已经创建 `AgentTask`，返回 `taskId`，并记录模型回合、工具调用、工具结果和最终状态。生产客服仍必须增加会话历史、限流、成本上限、PII 脱敏和人工接管；当前审计摘要仍保留在任务事件和步骤中，尚未接入独立会话存储和审计检索系统。

### P1.5 RAG 仍是本地演示能力

当前知识库是本地词法检索，ACL 由应用内角色过滤。生产需要真实文档来源、索引更新、租户隔离、文档版本、引用有效性、删除传播、检索超时和无证据降级。没有证据时必须明确回答无法确认，不能让模型补写政策。

## 4 P2 运维和质量缺口

- 将 `traceId` 接入 OpenTelemetry trace/span，并记录模型延迟、工具延迟、token、重试、审批等待时间和失败分类。
- 增加结构化日志、PII/密钥脱敏、日志留存和审计查询权限。
- 为应用和数据库增加 liveness/readiness 探针；当前自定义 `/api/v1/health` 固定返回 UP，不能证明数据库和下游可用。
- Compose 中的开发密码、未固定镜像摘要和无资源限制配置不能直接用于生产。
- 增加 Postgres Testcontainer/真实 PostgreSQL 集成测试、迁移回滚测试、双实例并发测试、故障注入、压测和容量基线。
- 评估集需要线上模型版本、样本量、延迟、成本、拒答率、越权阻断率和回归阈值；离线 25 条样例不能代表线上质量。
- 设置模型、工具和提示词版本；任何升级都应先跑评估集和安全回归。

## 5 建议的生产化顺序

### 阶段 A：先达到可控试点

1. 接入真实认证，移除客户端可伪造的角色头。
2. 强制 JDBC/PostgreSQL，补齐事务、乐观锁和 Outbox。
3. 只接入一个只读外部系统，完成超时、限流、审计和压测。
4. 高风险写操作继续保持模拟，先验证审批、拒绝、人工处理和重复请求。
5. 接入 OpenTelemetry、日志脱敏和基础告警。

### 阶段 B：小流量真实写操作

1. 只选择一个有明确幂等键和状态查询的写操作。
2. 增加外部系统沙箱、对账任务和人工处理队列。
3. 完成未知副作用、下游超时、消息重复和进程重启演练。
4. 以 allowlist 租户和 allowlist 操作灰度，默认 fail closed。

### 阶段 C：扩大范围

1. 扩大工具和角色前先更新权限矩阵、威胁模型和评估集。
2. 为每个真实工具提供独立契约测试、幂等证明和回滚/补偿说明。
3. 以 SLO、成本、越权阻断率和人工介入率作为发布门槛，而不是只看单元测试通过。

## 6 可执行的上线门槛

以下条件全部满足，才可以进入生产试点：

- [ ] 生产身份由 OIDC/JWT/mTLS 验证，应用不信任客户端角色头。
- [ ] 生产配置禁止 `AGENT_PERSISTENCE=memory`，数据库连接池和迁移已验证。
- [x] 每次任务快照、对应审计事件和待发布 outbox 记录已通过 `TaskAuditWriter` 在同一资源事务中写入。
- [x] Outbox 发布器已具备失败退避、租约领取和幂等发布标记。
- [ ] 接入真实下游事件总线、死信处理、监控和告警。
- [ ] 多实例同时创建、审批、取消和恢复测试通过。
- [ ] 所有真实写工具都有业务幂等键、状态查询和未知副作用处理。
- [ ] 真实模型和外部工具都有连接/读取超时、预算、限流、有限重试和熔断。
- [x] `/agent/chat` 已具备基础 taskId 和事件时间线。
- [ ] `/agent/chat` 补齐会话审计、PII 脱敏、成本上限和人工接管。
- [ ] liveness/readiness、日志、指标、trace、告警和回滚演练通过。
- [ ] 完成 PostgreSQL 重启、应用重启、数据库中断、模型超时、工具 500、重复消息和审批并发演练。
- [ ] 评估集、红队测试、压测、成本和 P95 指标都有真实环境证据。
- [ ] 发布说明明确列出已实现能力、未实现能力、值班手册和人工处理路径。

## 7 本仓库下一步最值得继续做的三项代码工作

1. 用认证主体替换 `X-User-Id/X-Role`，保留演示实现作为测试 profile。
2. 将任务执行拆成命令队列和 Worker，统一工具超时、重试、幂等和未知副作用状态。
3. 增加 `task_checkpoints`、版本化状态迁移和 Outbox，确保任务状态、checkpoint 和审计事件可恢复、可重放、可追溯。
