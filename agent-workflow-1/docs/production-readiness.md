# 生产就绪审查与上线门槛

## 本地业务接入增量说明

2026-10-27 本轮增加独立本地订单/支付服务、独立 MySQL 与合成数据，HTTP 模式覆盖只读查询、异步退款、状态轮询对账、人工处理和操作审计；修复 JDBC 写任务提前成功及结构化查询结果丢失问题，并改为逐条命令租约和版本校验。见 [业务接入说明与流程图](business-integration.md)。以下旧沙箱描述适用于默认模式；本轮不等于真实支付/承运商生产接入，也没有关闭租户隔离、任务心跳、监控值班、审计 Sink 和灾备等其余缺口。

## 结论

当前版本不能直接对接生产资金或承运商系统。它已经达到“可运行、可测试、可演示、可写本地业务库、可双实例运行”的水平：MySQL 中已实现订单、支付、退款、物流、地址变更和工单的真实读写，写操作必须经过审批并走事务性 Outbox；下游支付/物流调用仍是沙箱适配器，JWT 认证和审批职责分离已实现，双实例并发验收已通过，但企业 IdP 联调、令牌生命周期、真实下游接入和运维能力尚未完成。

当前全量测试通过（56 项），并已在本地 Docker MySQL 上完成查询、退款、改地址、发货和 Outbox 结算的手工端到端验证，以及真实签名令牌下的伪造头忽略、角色拒绝、职责分离和审批落库验证。双实例验收脚本在独立 schema 上完成 73 项检查（同幂等键创建、并发审批、审批/取消竞争、实例停机接管、过期任务恢复和生产门禁）。测试通过不等于生产系统已经完成身份、数据、并发、外部依赖和运维验收。

本次补充的代码改进：DeepSeek 多轮 Tool Calling 网关现在使用 `agent.deepseek.timeout-seconds` 设置连接/读取超时，并对瞬态错误和 429 限流做最多一次有限重试。只读模型请求可以安全重试，但真实业务写操作不能套用这条策略。

## 2 阻断上线的 P0 问题（P0.4 已关闭）

### P0.1 身份认证和权限来源不可信（应用侧已实现，待 IdP 联调）

原实现由 `TaskController` 和 `AgentChatController` 直接读取 `X-User-Id`、`X-Role`，任何能访问服务的人都可以伪造主管或管理员身份。现在已改为 Spring Security OAuth2 Resource Server：

1. 所有业务端点要求 `Authorization: Bearer <JWT>`，签名、issuer、audience 和过期时间由 `JwtDecoder` 校验；缺失或无效令牌返回 JSON 401。
2. 用户身份只取签名令牌的 `sub`；角色来自可配置 claim（默认 `roles`，支持 `realm_access.roles` 等点路径），未知角色被丢弃，令牌没有任何已知角色时拒绝。
3. 控制器通过 `@AuthenticationPrincipal Jwt` 解析 `AuthenticatedUser`，业务代码不再读取身份请求头；客户端提交的 `X-User-Id`/`X-Role` 被忽略。
4. 过滤链要求 `SUPERVISOR`/`ADMIN` 才能调用审批、拒绝和恢复接口，`AgentApplicationService` 再次校验角色，并执行职责分离：申请人不能审批自己的任务。
5. `local` 模式使用 HS256 便于离线演示，密钥不足 32 字节会拒绝启动；`oidc` 模式缺少 issuer/JWK 配置会拒绝启动。开发令牌端点仅在 `local` 且显式开启时存在。

仍需完成的生产工作：

1. 与企业 IdP 做真实 discovery/JWK、audience 和角色映射联调，并验证令牌过期、轮换、吊销和时钟偏差。
2. 明确租户/组织边界、权限目录和审批人范围；当前职责分离只比较 `sub`，尚未引入多租户和代理审批规则。
3. 在网关层限制转发头，确保只透传 `Authorization`，并补齐认证失败审计、告警和 rate limit。

### P0.2 真实下游适配器和业务幂等仍待接入

本地业务库写入已经实现：`JdbcCommerceRepository` 在同一事务中写退款/地址变更/物流单和 `integration_commands`，业务表上有退款、物流、地址变更和命令的唯一幂等键，调度器用租约和 `SKIP LOCKED` 领取命令。但默认 `SandboxCommerceGateway` 只返回确定性单号，真实下游适配器仍必须处理：

- 下游超时、限流、5xx、部分成功和结果未知。
- 业务幂等键下沉到支付、订单和物流系统（当前键由 `taskId + tool + args` 生成，尚未传递到真实提供商）。
- 请求签名、凭据轮换、连接池和 TLS。
- 外部状态查询、对账和 `UNKNOWN` 命令的人工处理队列。

不能把 `SandboxCommerceGateway` 换成“真实 HTTP 调用”就直接上线。写操作必须保持四种结果：“请求已受理”“执行成功”“执行失败”“状态未知”，并对状态未知进入人工处理或对账队列。

### P0.3 默认内存存储和完整事务边界

默认配置仍是 `AGENT_PERSISTENCE=memory`，进程重启会丢失任务和事件。JDBC 适配器已经补齐：

- HikariCP 连接池、连接超时和 `initializationFailTimeout=1`，JDBC 模式连接失败时启动直接失败。
- MySQL/Flyway `V1..V5` 覆盖任务、步骤、审计事件、审计 Outbox 和业务表。
- `TaskAuditWriter` 把任务快照、审计事件和待发布记录放在同一资源事务中写入。
- `CommerceCommandDispatcher` 用租约、退避和最大尝试次数处理退款/物流/地址变更命令，超时进入 `UNKNOWN`，失败达到上限进入 `FAILED`。
- 仍缺少 Outbox 归档/保留策略、真实审计事件总线和死信告警。

生产改造要求：

1. ~~生产配置强制 `AGENT_PERSISTENCE=jdbc`，memory 只允许测试；当前默认仍是 memory，需要部署层校验。~~ 已由 `ProductionConfigurationGuard`（`@Profile("prod")`）实现：prod 下 memory 仓储、local 认证、dev token、演示种子、默认数据库密码都会导致启动失败。开发默认仍为 memory，部署必须显式激活 `prod`。
2. 完善 HikariCP 泄漏检测、只读连接和按环境容量调参。
3. 把审计 Outbox 接到真实事件总线/SIEM，并补齐死信、归档和保留策略。
4. 把 commerce Outbox 接到真实支付/物流适配器，定义 `UNKNOWN` 的人工处理和对账流程。
5. ~~复核 `user_id + idempotency_key`、业务幂等键和审批版本约束，并在双实例下做竞争测试。~~ 已完成：创建路径移除进程内 `synchronized` 和读前置检查，直接依赖唯一约束并由重复键回退解析；审批使用 `SELECT ... FOR UPDATE`；双实例 73 项检查通过。

### P0.4 多实例幂等与竞争（已关闭，保留验收记录）

原实现依赖 `AgentApplicationService.create` 的 `synchronized` 和审批的对象锁，只在单进程内有效。现在：

- 创建路径不再做“先查再插”，也不使用进程内锁；并发请求直接 INSERT，由 `tasks(user_id, idempotency_key)` 唯一约束裁决，重复键由仓储回退查询并返回同一任务。JDBC 模式会记录 `Unique constraint resolved concurrent create` 作为命中证据。
- 审批/取消/恢复通过 `tasks.require` 的 `SELECT ... FOR UPDATE` 串行化，并结合状态机拒绝非法迁移；终态操作保持幂等空操作。
- 退款、地址变更、物流写操作在业务表唯一幂等键和 `integration_commands(task_id, tool_name, idempotency_key)` 唯一键保护下，同一事务写业务记录与命令。
- `CommerceCommandDispatcher` 使用 `FOR UPDATE SKIP LOCKED` 租约领取，过期租约可被其他实例接管。
- `RecoveryService` 在启动时扫描超过 `AGENT_RECOVERY_STALE_SECONDS` 的 `CREATED/PLANNING/RUNNING` 任务并转入 `RECOVERY_REQUIRED`，不会误伤其他实例上的活跃任务。

双实例验收（`scripts/two_instance_acceptance.py`，2026-10-27）结果 73/73：

- 6 个并发同幂等键创建返回同一 task id，每个键只有一行；重复键回退路径被真实触发。
- 并发审批两个实例都返回 200，任务只成功一次，只写一条退款、一条 outbox 命令和一个 `TOOL_EXECUTED` 事件。
- 审批与取消竞争 3 轮均为单赢家：`SUCCEEDED` 且有一次写入 XOR `CANCELLED` 且无写入，无重复命令键。
- 停止实例 A 后实例 B 保持就绪；过期 `RUNNING` 任务被恢复，活跃 `RUNNING` 任务不受影响。
- `prod` profile 在默认不安全配置下退出码为 1 并列出全部违规项。

仍需完成：MySQL 重启/主从切换下的连接恢复、死锁重试指标、Outbox 长时间积压和真实下游超时演练。

### P0.5 同步 HTTP 执行不适合长任务

当前 `POST /tasks` 会在 HTTP 请求中完成规划和工具执行，deadline 默认 30 秒。真实模型和业务系统可能超过网关超时，客户端断开也不代表服务端停止了外部写操作。

生产改造要求：

```text
POST /tasks -> 写入任务 + 投递命令 -> 202 Accepted + taskId
Worker -> 规划/审批/执行 -> 持久化状态和事件
Client -> GET /tasks/{id} 或订阅事件
```

需要队列、Worker、取消语义、死信队列和人工处理队列。审批也应是独立命令，不应依赖原始 HTTP 请求仍然存活。

## 3 P1 重要缺口

### P1.1 Checkpoint 不是独立持久化状态

当前 `Checkpoint` 是执行循环中的对象，主要通过 `CHECKPOINT_SAVED` 审计事件表达；恢复时根据已成功的 `task_steps` 推导下一步。进程可能在外部写操作已产生效果、但步骤尚未提交时崩溃，恢复无法仅凭本地状态判断外部结果。

生产方案：

- 增加独立 `task_checkpoints` 表和版本号。
- 写工具执行前生成业务幂等键并持久化。
- 写工具返回不确定时进入 `UNKNOWN_SIDE_EFFECT`，禁止自动重放。
- 通过外部查询、对账或人工审批确认后再关闭任务。

### P1.2 RetryPolicy 尚未覆盖工具执行

当前 `RetryPolicy` 主要用于 DeepSeek 规划请求；`AgentApplicationService.executePlan` 没有一个统一的工具重试执行器。生产不能用“所有异常都重试”的方式补上，因为写操作可能重复产生副作用。

建议新增 `ToolExecutor`，按工具契约声明：

| 工具类型 | 可重试条件 |
| --- | --- |
| 只读查询 | 连接失败、429、部分 5xx，可在 deadline 内有限重试 |
| 幂等写操作 | 只有下游确认幂等键后才允许有限重试 |
| 非幂等写操作 | 不自动重试，状态未知进入人工队列 |
| 参数/权限/业务拒绝 | 不重试 |

### P1.3 ContextBuilder 没有接入完整规划链

`ContextBuilder` 已经可以限制当前任务请求和最近步骤，但当前主规划器仍主要接收原始 request；聊天现在有任务审计，但还没有独立的 conversation context 存储。生产模型上下文需要：

- 只传当前任务、当前租户和必要的授权证据。
- 明确截断、token 预算和敏感字段脱敏。
- 把数据库结构化状态作为事实源，不把模型历史当作最终状态。
- 记录 prompt/model/version，便于复盘和成本分析。

### P1.4 聊天入口的生产审计仍需完善

`/api/v1/agent/chat` 现在已经创建 `AgentTask`，返回 `taskId`，并记录模型回合、工具调用、工具结果和最终状态。生产客服仍必须增加会话历史、限流、成本上限、PII 脱敏和人工接管；当前审计摘要仍保留在任务事件和步骤中，尚未接入独立会话存储和审计检索系统。

### P1.5 RAG 仍是本地演示能力

当前知识库是本地词法检索，ACL 由应用内角色过滤。生产需要真实文档来源、索引更新、租户隔离、文档版本、引用有效性、删除传播、检索超时和无证据降级。没有证据时必须明确回答无法确认，不能让模型补写政策。

## 4 P2 运维和质量缺口

- 将 `traceId` 接入 OpenTelemetry trace/span，并记录模型延迟、工具延迟、token、重试、审批等待时间和失败分类。
- 增加结构化日志、PII/密钥脱敏、日志留存和审计查询权限。
- 为应用、数据库和下游增加 liveness/readiness 探针；`/api/v1/health` 返回后端类型，`/api/v1/health/readiness` 已校验业务库，但下游网关和队列尚无独立探针。
- Compose 中的开发密码、未固定镜像摘要和无资源限制配置不能直接用于生产。
- 增加 MySQL Testcontainer 集成测试、迁移回滚测试、故障注入、压测和容量基线；双实例竞争已有独立验收脚本覆盖。
- 评估集需要线上模型版本、样本量、延迟、成本、拒答率、越权阻断率和回归阈值；离线 25 条样例不能代表线上质量。
- 设置模型、工具和提示词版本；任何升级都应先跑评估集和安全回归。

## 5 建议的生产化顺序

### 阶段 A：先达到可控试点

1. 接入真实认证，移除客户端可伪造的角色头。
2. 强制 JDBC/MySQL，补齐事务和 Outbox 运维；生产配置门禁与双实例锁竞争验证已完成。

5. 接入 OpenTelemetry、日志脱敏和基础告警。

### 阶段 B：小流量真实写操作

1. 只选择一个有明确幂等键和状态查询的写操作。
2. 增加外部系统沙箱、对账任务和人工处理队列。
3. 完成未知副作用、下游超时、消息重复和进程重启演练。

### 阶段 C：扩大范围

1. 扩大工具和角色前先更新权限矩阵、威胁模型和评估集。
2. 为每个真实工具提供独立契约测试、幂等证明和回滚/补偿说明。
3. 以 SLO、成本、越权阻断率和人工介入率作为发布门槛，而不是只看单元测试通过。
